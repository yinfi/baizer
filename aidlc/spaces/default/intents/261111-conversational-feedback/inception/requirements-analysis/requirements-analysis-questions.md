## Q2 变更留痕（两次，最终为 B）

**第一轮：D → 「需要 Token」**（用户：「如果没有token，整个功能就失效，不能使用就行」）
零凭据下插件没有提交能力，只能生成预填链接由用户在浏览器手动提交，不满足「插件真能把 issue 提交上去」的诉求。上一版 PRD 中所有「Q2=D 推导」的改动（`FR3.12` URL 长度降级、`FR3.13` 手动粘贴、`FR3.8` 提交结果不可感知等）随之作废。

**第二轮：在三项新方案中选定 B**（用户：「用我自己的 git 账号 token 写到代码逻辑里面来提交，不让用户填权限」，并追问「能否通过非对称方式实现对 token 的加密？」）

经确认**非对称加密在本场景不成立**，理由是结构性的而非算法问题：插件必须在用户机器上持有明文 token 才能发出 HTTPS 请求；私钥随包分发等于没加密，私钥留在服务端则插件拿不到明文、只能把请求发给持有私钥的一方——那**正好就是中转服务**。能执行该请求的客户端就能被改造成替别人执行，安全边界不可能划在攻击者自己控制的代码里面。故只有三种状态：秘密在服务端（A）、秘密是用户自己的（C）、秘密是公开的（B）。

用户在 A / B / C 中选定 **B**：

| 选项 | 用户配置 | token 是否公开 | 能否快速止损 |
|---|---|---|---|
| A. 中转服务 | 零 | 否 | 能，服务端随时关停 |
| **B. token 进插件（最小权限）** | 零 | 是，但危害被限制在一个仓库的 issue 区 | **不能，要等一轮发布** |
| C. Device Flow | 点一次授权 | 否 | 能，用户可自行撤销 |

**B 的既定代价（用户已知悉并接受）**：token 随每个发行包分发、等于公开；所有 issue 以发布方账号发出；一旦被滥用，止损要等一轮「轮换 + 重新构建 + 用户升级」，**没有即时开关**。权限收到最小：fine-grained PAT、仅授权 `yinfi/baizer`、仅勾 `Issues: write`。

**B 带来的三条新增需求**（见 `requirements.md`）：凭据注入契约（`FR4.2`/`FR4.6`/`FR4.7`/`NFR7`）、自读风险与插件目录读隔离（`FR6.7`）、提交前显式确认（`FR3.7`）。

**一项可能推翻 B 的技术风险**（`[assumption]` A1，必须前置验证）：GitHub 的 secret scanning 会自动检测公开仓库中的 GitHub 格式 token 并可能自动撤销。`dist/main.js` 作为 Release 资产公开发布，若其中含明文 `github_pat_*`/`ghp_*` 字符串，存在被 GitHub 自动撤销的风险——现象是「昨天还好、今天所有用户全部 401」，极难定位。**验证方式**：用一个测试 token 走一遍完整发布流程观察。**若成立，Q2=B 需要重新决策。**

## Q1. [产品] 反馈入口放在哪、长什么样？

需求说的是「在使用过程中遇到问题就能反馈」，所以入口的**可达范围**是这题的核心，不是按钮的样式。

- A.（推荐）**Workbench 头部新增反馈图标按钮 + 命令面板命令 `baizer:feedback`**。点按钮新开一个专用反馈 tab，复用现有对话 UI 与模型链路；命令面板保证用户在笔记编辑、Guardian 使用中也能发起反馈
- B. 只做一个独立弹窗（Modal）内嵌对话，不占用 tab —— 好处是不打断当前对话，代价是要重造流式渲染、工具时间线、审批卡片一整套 UI（违反 DRY）
- C. 只加命令面板命令，不加可见按钮 —— 最省事，但发现性最差，「用户想反馈时找不到入口」正是本需求要解决的问题
- X. Other (please specify)

[Answer]: A. 头部按钮 + 命令面板命令 + 专用反馈 tab

## Q2. [架构] 提交 issue 用哪种 GitHub 鉴权方式？

这是本需求**最大的一个取舍**，直接决定用户上手成本与后续维护负担。

- A. 用户在设置页填**自己的 fine-grained PAT**（仅勾 `Issues: write` 权限，限定 `yinfi/baizer` 一个仓库）—— 权限最小、安全性最好，但用户要去 GitHub 手动建 Token，上手成本高
- B. 用户填 **classic PAT**（`public_repo` 范围）—— 比 A 好填，但权限范围更大（可写用户所有公开仓库），最小权限原则上有让步
- C. **GitHub OAuth Device Flow** —— 用户点「连接 GitHub」→ 得到一个码 → 在 `github.com/login/device` 输入即完成授权。体验最好、无需用户理解 Token 概念，但需要项目方**注册并持有**一个 OAuth App 的 `client_id`，多一份长期维护责任
- D. **完全不要 Token** —— 插件只负责生成草稿，然后打开浏览器里预填好的 `github.com/yinfi/baizer/issues/new?title=...&body=...` 页面，用户自己点「Submit new issue」。零凭据、零权限、移动端最稳，代价是最后一步要用户手动完成，且正文受 URL 长度限制（超长正文需降级为复制到剪贴板）
- X. Other (please specify)

[Answer]: D.（**已于后续两轮变更中改为 B，见上方「Q2 变更留痕」**）

## Q3. [产品] 模型不可用时，要不要补一个「表单式反馈」兜底？

澄清对话依赖 LLM，LLM 依赖网络。所以**离线时对话式反馈这条路本身就走不通**——这不是一个边角情况，而是本功能最实质的降级缺口。

- A. **不做**。LLM 不可用时给出明确提示（说明当前无法进行对话式反馈及原因），不做替代路径 —— 实现最简，但离线用户彻底无法反馈
- B. **做**。提供一个静态表单 Modal（直接填标题、问题描述、复现步骤），跳过智能体澄清，走与对话式反馈同一条提交通道 —— 保证「离线也能留下反馈」，代价是多一套表单 UI 与字段定义，且需要与模板渲染规则保持一致（避免两套字段定义）
- X. Other (please specify)

[Answer]: A. 不做兜底，只给明确提示

## Q4. [产品] 目标仓库是否允许用户配置？

本插件是开源项目，用户可能自己 fork 或自行部署。反馈该收进原仓库还是用户自己的仓库，是产品定位问题。

- A. **硬编码 `yinfi/baizer`**。所有反馈都汇到原项目，插件不提供配置项 —— 最简单，符合「给上游报 bug」的直觉
- B. **设置页可配 `owner/repo`，默认 `yinfi/baizer`** —— fork 用户可把反馈收进自己的仓库，但多一个配置项与一类配错的可能（仓库不存在/无权限），需要在「测试连接」里覆盖
- X. Other (please specify)

[Answer]: A. 硬编码 `yinfi/baizer`，不提供配置项

## Q5. [产品] 提交前查到相似 issue 时，怎么处理？

- A.（推荐）**展示候选列表，让用户选**：「追加评论到已有 issue」或「仍然新建」。智能体不替用户判断是不是同一个问题
- B. **只提示候选并给出链接**，不提供自动追加评论，用户自己决定去不去评论 —— 实现更简单，也不会产生额外的对外写操作
- C. **不做去重**，澄清完直接新建 —— 最简，但容易产生重复 issue，长期会污染仓库
- X. Other (please specify)

[Answer]: A. 展示候选，用户选「追加评论」或「仍新建」（Q2=B 下两者均可由插件自动执行，无降级）

## Q6. [产品] 诊断信息默认带还是默认不带？

诊断信息指：插件版本、Obsidian 版本、平台、当前 provider 类型、最近一次错误摘要。它决定了 issue 的可定位程度，也决定了隐私暴露面。

- A.（推荐）**默认附带，用户可在提交预览里逐项取消** —— issue 质量最高（模板里 plugin-version / obsidian-version / platform / provider 都是必填项，不带就等于让用户手填），且预览环节给了用户完全的控制权
- B. **默认不带，用户逐项勾选才带** —— 最保守，但多数用户不会勾，导致 issue 缺少定位信息、需要来回追问
- C. **永不附带** —— 隐私最强，但 issue 质量会显著下降
- X. Other (please specify)

[Answer]: A. 默认附带，用户可在预览里逐项取消（**注**：附带后正文变长不再构成问题——Q2=B 走 API 写入，不受 URL 长度限制）

## Q7. [产品] 现有的 AI 回复「👎」要不要接入反馈流程？

现状：AI 消息操作栏的 👎 会展开内联输入问「哪里不好」，提交后写入长期记忆（`retainLesson`）并当场重新生成一版回答。这与 GitHub issue 无关，是两件不同的事。

- A. **接入**：👎 的「原因」提交后，除现有行为外，额外给一个「把这个不满变成一条反馈」的按钮，点了带着已有原因进入反馈会话 —— 复用用户已经付出的输入成本，反馈转化率最高
- B. **不接入**：保持现状，反馈只走独立入口 —— 两条链路彻底解耦，改动面最小，不会让「点踩」这个轻动作带上对外提交的预期
- X. Other (please specify)

[Answer]: B. 不接入，两条链路解耦

## Q8. [架构] 反馈会话要不要复用用户日常对话的上下文？

现状：`BaseChatRuntime.prepareTurn` 会无条件注入长期记忆召回（`recallForPrompt` + Mental Model 块），并注入当前笔记/反链等环境上下文。

- A.（推荐）**不复用**：反馈会话是干净会话——不注入当前笔记与反链（`requirements.md` FR2.7 已定），长期记忆召回也不注入。理由：反馈正文最终会**公开发布**，用户个人偏好/笔记内容的任何泄漏都是不可逆的；隔离比事后过滤可靠
- B. **复用**（与普通对话一致）：智能体能更懂用户语境、提问更少，但记忆内容进入提示词后有可能被写进公开 issue，只能靠提示词约束，与 FR6.4 存在张力
- X. Other (please specify)

[Answer]: A. 不复用，反馈会话是干净会话（不注入长期记忆、不注入环境上下文）
