# Rollback Runbook

## 结论

回滚不是服务端动作，而是两条独立路径的组合：用户侧依赖 Obsidian 客户端内置的插件版本历史手动降级；仓库侧通过撤回/编辑有问题的 GitHub Release 并尽快发布修复版本，阻止新用户继续安装到坏版本。两条路径互不依赖，必须都执行。

## 背景

Obsidian 插件没有服务端部署目标，因此不存在"把流量切回旧版本"意义上的回滚。已安装用户的插件版本是在其本地客户端固化的，直到该客户端下一次检测更新才会变化；回滚的本质是"阻止坏版本扩散"+"让已装坏版本的用户能够降级"，而非"立即撤销所有用户的坏版本"。

## 触发条件

发现刚发布的版本（Publish 之后）存在以下任一问题：
- 构建产物本身损坏（如 `main.js` 加载后插件无法启动）
- 功能性缺陷造成数据丢失或损坏风险（尤其是涉及 session/vault 文件写入的路径——本次重构直接涉及会话持久化层，需格外关注）
- 与 `minAppVersion` 声明的 Obsidian 版本不兼容

## 仓库侧处置步骤

1. **立即撤回或编辑 Release**：
   - 若发布后极短时间内发现问题、尚未大规模扩散：直接在 GitHub Release 页面删除该 Release（保留 tag 或一并删除，取决于是否要复用版本号——建议不复用，废弃版本号比复用更不容易引发混淆）。
   - 若已有用户下载：不删除 Release，而是编辑该 Release 的说明，在顶部加注明显的警告（如"⚠️ 该版本存在 XX 问题，请勿安装，正在修复中，参见 vX.Y.Z+1"）。
2. **发布修复版本**：
   - 按 `deployment-strategy.md` 的标准流程走一遍完整发布，版本号按 semver 递增 Patch（如 `1.1.0 → 1.1.1`），不复用或回退已发布过的版本号。
   - 若问题严重（数据损坏风险），修复版本的 Release Notes 必须明确说明"此版本修复了 vX.Y.Z 中的 <问题摘要>，建议从 vX.Y.Z 升级的用户尽快更新"。
3. **验证修复版本**：复用 `release.yml` 的标准质量门禁（build+test+lint），且针对本次触发回滚的具体缺陷补充一条回归测试（遵循 construction phase 的测试要求：针对具体 bug/缺陷的定向回归用例）。

## 用户侧处置路径（本仓库侧无法代为执行，但需在文档中告知）

1. 用户在 Obsidian 内 `设置 → 第三方插件 → Baizer` 查看当前安装版本。
2. 通过 Obsidian 内置的插件版本历史功能（或手动从 GitHub Release 页面下载旧版本的 `main.js`/`manifest.json`/`styles.css` 覆盖本地插件目录）降级到已知良好版本。
3. 等待修复版本发布后重新升级。

## 不适用的回滚手段

- **数据库迁移回滚**：本项目无数据库，会话持久化层（本次重构的核心变更）落地在 vault 内的 JSONL 文件，若该层的数据格式发生不兼容变更，需要在 `deployment-strategy.md` 升级流程中额外评估"旧格式数据能否被新版本插件读取"，但格式迁移兼容性评估属于 Code Generation / Build and Test 阶段的既有验收范畴，不属于本 runbook 的回滚范围——本 runbook 假设已通过的构建等同于格式兼容。
- **流量切换类回滚（DNS/负载均衡切换等）**：不适用，理由同 `deployment-strategy.md` 的"不采用的策略"章节。

## 验证

本 runbook 未经过实战演练（本项目当前没有发生过需要回滚的发布事件）；步骤基于 Obsidian 插件发布机制的既有事实（GitHub Release 可编辑/删除、客户端插件版本历史功能存在）推导得出，首次真实触发时需据实际情况校正步骤细节。
